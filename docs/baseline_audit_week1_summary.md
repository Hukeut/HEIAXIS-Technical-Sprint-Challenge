# Baseline Audit Week 1: Assumptions and Limitations

A short summary, per the sprint brief's end-of-week checkpoint requirement. Full design reasoning lives in `docs/baseline_audit_data_model.md` and `docs/baseline_audit_planning_note.md`, this is only what to keep in mind when reading Week 1's results.

## Assumptions

Department and office are treated as the same entity, `departments.csv` reuses the same five names and staff counts already in `staff.csv`, rather than modeling a separate department roster. `ANALYSIS_AS_OF` (the reference "now" for every overdue and days-elapsed calculation) is a fixed constant set to the synthetic term's end date, not the real system clock, since this is a static 7-week dataset, not a live feed. Every day-based threshold (21 days for a stale referral or an overdue case, 14 and 28 days for the confidence tiers) was kept numerically equivalent to the original Early Signal Intelligence week-based thresholds rather than independently tuned, there's no real outcome data yet to tune against. "Department under capacity pressure," one of priority's risk factors, is a relative comparison, a department's cases-per-staff at or above the median across departments this term, not a fixed number, so what counts as elevated shifts with the data rather than being a stable operational definition. For action-plan-sourced continuity gaps, the `workflow_id` column in `baseline_continuity_gaps.csv` actually holds the plan_id, action plans don't have a workflow_id of their own, plan_id is the natural identifier for that row.

## Limitations

No API yet, the six required endpoints are Week 2 scope per the brief and haven't been started. All the thresholds above are placeholders in the same sense `docs/architecture.md` already flags for the original detector's thresholds, they'd need to be set collaboratively with real institutional staff against their actual tolerance for false positives, not chosen unilaterally by engineering. Priority's risk factors (severe delay, missing ownership, cross-department involvement, an overdue action plan, department capacity pressure) are counted, not weighted, deliberately, so every factor counts equally even though an institution might reasonably judge some more urgent than others in practice, there's no per-institution override for that yet. The original Early Signal Intelligence outputs (`flagged_students.csv`, `continuity_gaps.csv`) and the new Baseline Audit outputs are not cross-referenced, a student could appear in both with no explicit link between the two signals, a reviewer currently has to check both lists separately. Multi-department detection only looks at currently open, simultaneous activity, it won't catch a case that was uncoordinated in the past but has since been separately closed by both departments without anyone noticing the overlap while it was happening. And as with the rest of this project, everything here runs on synthetic data generated by this same repository, none of it proves the detection logic works on real students, only that it behaves as intended on data built to match that intent, see `docs/evaluation_logic.md` for why that distinction matters.
