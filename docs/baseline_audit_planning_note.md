# Baseline Audit Sprint: Planning Note

One page, submitted before writing any code, per the sprint brief's Section 2.

**Understanding of the goal.** The Early Signal Intelligence prototype already proves the core HEIAXIS thesis at a small scale: institutions are usually fine at noticing a problem, they fail at following through on it. Baseline Audit extends that same thesis from individual student cases to the operational layer underneath them, where in the institution's workflow structure things are actually breaking down: which departments are overloaded, which referrals and action plans go unresolved, which workflows have no owner. The technical goal is to generalize the existing continuity-gap logic against a richer, more realistic schema, and add a department-level bottleneck view and action-plan tracking alongside it, without losing the thing that made the first prototype work: every output stays explainable, with confidence and priority reported as two distinct, separately computed values, never blended into one score.

**Scope.** In scope: extending `generate_data.py` with the four required tables (`service_interactions`, `departments`, `action_plans`, updated `students`) plus their deliberate messiness, extending cleaning and validation against the new schema with a data-quality report, four new analysis outputs (bottleneck summary, continuity gaps, action-plan summary, student review list), the six required API endpoints with filtering, and tests for all of it. Out of scope, per the brief: real data of any kind, production deployment or a real database, authentication, a frontend, autonomous action on students, and black-box ML. Also out of scope by my own judgment: rebuilding the existing repository from scratch, this continues from what already exists.

**Time allocation.** Week 1 (~9h): 2h schema and generator extension, 2h cleaning and the data-quality report, 4h analysis functions with tests written alongside each one, 1h buffer before the checkpoint. Week 2 (~9h): 1h API scaffolding, 4h endpoints, filtering, and error handling, 2h endpoint tests, 2h documentation and walkthrough prep.

**Reuse, modify, replace.** Reuse: the Flask self-explanatory JSON envelope pattern already in `src/api.py`, and the count-and-report-every-correction philosophy already in `src/cleaning.py`. Modify: `generate_data.py`, `cleaning.py`, and `signals.py` extended with new functions for the new tables, existing Early Signal Intelligence logic stays intact rather than being torn out, since the brief treats this as additive. Replace: nothing wholesale. The existing `office_caseload_summary` logic generalizes directly into the new department bottleneck summary, since they're the same idea over a richer schema.

**Main technical choices.** Stay fully rule-based, no ML, consistent with both this project's existing approach and the brief's explicit ban. Keep confidence and priority as two separately computed fields on every row. Centralize every threshold (referral-open age, overdue window, no-follow-up window) as named, documented constants rather than inline magic numbers. Continue with Flask for the API rather than switching frameworks, the brief allows it and nothing about this sprint's scope argues for a different one.

**AI tool use and verification.** I use an AI assistant for scaffolding, refactors, and documentation drafts, but every function is syntax-checked and run against the test suite before being accepted, every generated commit message is reviewed for accuracy against what actually changed, and no threshold or business rule suggested by the tool is accepted without checking it against the brief's own requirements first. Detector logic, schema decisions, and scope calls stay mine.

**Three risks.** First, reconciling two overlapping schemas (`care_interactions`/`office` from the original prototype versus `service_interactions`/`department` here) without the codebase splitting into two parallel systems. Second, making confidence and priority genuinely distinct in practice, not just two names attached to the same underlying number. Third, the 8-10h/week budget is tight for schema extension plus four new analysis outputs plus tests in week 1 alone, risk of the API week absorbing overflow.

**Definition of success.** One repository, one pipeline, producing all four required outputs plus the data-quality report, every row explainable with confidence and priority kept distinct, a read-only API exposing all six endpoints with stable JSON shapes even when empty, tests that would actually catch a real regression, and every decision defensible in the final walkthrough, including what was cut and why.
